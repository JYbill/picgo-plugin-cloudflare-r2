# 断言、测试数据与注释

## 优先验证的行为

单元测试优先验证：

- 输入到输出的有意义转换。
- 可能被错误实现的分支或规则。
- 空输入、重复输入、缺失字段、非法类型、不支持状态等边界。
- 明确的错误消息或失败模式。
- 调用方确实依赖的协作者交互契约。

成功路径只在能保护归一化、转换、兼容性或必要默认值时保留。否则优先覆盖失败、边界或明确规则。

## 断言质量检查

保留或新增断言前，逐项确认：

- 删除目标规则后，断言会失败。
- 断言检查的是调用方真正依赖的行为。
- expected 根据规则独立选择，没有从 setup 对象复制。
- 断言足够具体，失败时能定位回归点。
- 测试名称描述行为，不描述实现细节。

expected 即使使用 `toEqual()` 整体比较，只要它是独立定义并体现归一化、转换、过滤、排序、校验或默认值规则，就属于有效断言。

## 注释要求

所有单元测试的 `it`、`test`、`it.each()` 和 `test.each()` 块上方都写中文注释：

- `目的`：说明为什么要测这个场景。
- `总结`：说明测试最终保护的行为。

每个 `expect()` 断言块上方写 `期待`，说明要观察的输出、错误、调用或状态。多个 `expect()` 共同验证同一件事时，可以共用一条紧贴的“期待”注释；验证不同内容时分别写。

```ts
// 目的：验证只提供成对字段的一侧时会抛出明确错误。
// 总结：缺少配对字段会触发配置完整性校验。
it("rejects incomplete paired fields", () => {
  // 期待：校验时抛出成对字段必须同时填写的错误。
  expect(() => validateConfig({ publicKey: "value" })).toThrow(
    "publicKey 和 privateKey 必须同时填写或同时留空",
  );
});
```

注释要说明规则，不要只复述函数名或“测试正常运行”。

## 测试数据和命名

使用能表达规则的通用 fixture 名称，例如 `validInput`、`invalidInput`、`missingRequiredPair`、`emptyItems`、`duplicateItems` 和 `unsupportedState`。输入值要展示被测规则，不携带与规则无关的业务细节。
